1) Problem & constraints

Most motorcycle dashboards fail riders in one of three ways: information overload, poor glanceability, or zero flexibility. Riders need critical information instantly, without visual hunting, while moving at speed.

Design goal: A dashboard that communicates priority information in under ~0.5s per glance, and stays usable across daylight, night riding, rain, vibration, and gloves.
Constraints (non-negotiable) - Circular 4" OLED - Outdoor visibility (sun + night) - Gloves on → no touch-first UX - Fragmented rider attention - ESP32-class compute - IP68 sealed enclosure - Works across different motorcycles
Safety-critical Glanceability Embedded constraints Outdoor legibility

2) Users & insights

Primary users

  • Daily commuters
  • Touring riders
  • Custom / cafe / ADV riders
  • Riders upgrading from analog clusters

Key insights

  • Speed and warnings must be readable without focus.
  • RPM is pattern-based: ring + thresholds beat small digits.
  • Riders want control over what is shown (cognitive fit).
  • Navigation must be directional, not map-based.
  • Night riding punishes bright, busy UIs.

3) UX principles

1. Glanceable first
Primary values are readable in under ~0.5 seconds.
2. Hierarchy over density
Fewer elements, stronger prioritisation. No “data soup”.
3. Peripheral awareness
Warnings live on the edge, not in the center.
4. Contextual flexibility
Layout adapts to mode and preference without breaking hierarchy.
5. Fail gracefully
Missing data never breaks comprehension.

4) Information architecture

Prioritisation is everything. The interface is organised into tiers based on how often riders need the info and how risky it is to hunt for it while moving.

Tier 1 (always visible)

  • Speed
  • Critical warnings
  • Gear (optional/configurable)

Tier 2 (situational)

  • RPM (ring)
  • Fuel
  • Temp
  • Secondary battery voltage

Tier 3 (on-demand)

  • ODO
  • Trip A/B
  • Date/time
  • Navigation prompts

5) Interaction model

No touch-first gimmicks. The system is designed for gloves and motion using a simple physical control scheme.

Primary interactions

  • Physical buttons / crown
  • Short press vs long press
  • Context-aware control mapping
  • Auto-revert to ride mode after inactivity
Example mapping (draft) Rotate: cycle info cards Press: confirm / toggle view Long press: settings Hold (ride): reset trip (with confirm)
Interaction rule: nothing should require multiple steps while the bike is moving.

6) UI system

Layout logic

  • Center: speed (largest text, highest contrast)
  • Radial ring: RPM with thresholds (pattern-based)
  • Edge ring: indicator icons (turn, high beam, neutral, warnings)
  • Modular widgets: fuel / temp / battery / odo / trip

Typography + legibility

  • High x-height, bold numerals
  • No thin strokes
  • Numeric clarity > style
  • Distance readability tested (helmet posture)

Color & meaning

  • Red = immediate danger only
  • Amber = caution
  • Green/Blue = informational
  • OLED-safe palette, dark-first to reduce glare
UI components (draft) - Speed readout - RPM ring - Gear badge - Indicator ring - Widget cards (fuel/temp/battery/odo/trip) - Alert banners (rare, high priority)

7) Customization (as UX, not gimmick)

Customisation is framed as cognitive fit: riders can tailor the interface to their riding style without breaking the information hierarchy.

What users can tweak

  • Layout presets (Minimal / Touring / Sport)
  • RPM redline and shift-light behavior
  • Widget assignments
  • Units (km/h, mph), contrast modes
  • Theme palettes (OLED-friendly)
Rule: Customisation never changes core hierarchy. Speed + warnings remain dominant.

8) Navigation UX (smart restraint)

The dash displays glanceable navigation prompts; the phone does the heavy lifting. No maps, no scrolling, no clutter.

Navigation elements

  • Direction arrow
  • Distance to next turn
  • Optional street name (truncated)
  • Optional ETA
Why: Riders don’t read maps at speed — they glance for the next move.

9) Edge cases & failure modes

UX doesn’t stop when things go wrong. The interface prioritizes comprehension and clear recovery.

Examples

  • Lost CAN/sensor → placeholder + warning
  • Low voltage → dim UI + warning first
  • Overheat → simplified view + thermal alert
  • Night/day → auto-adjust with manual override
Fail-safe behavior (draft) - Default to readable state - Avoid flashing unless critical - Keep speed + warnings available - Provide clear “data source lost” messaging

10) Outcome & reflection

What this project demonstrates

  • Designing under hardware constraints
  • Safety-critical hierarchy & glanceability
  • Non-touch interaction design
  • Customization without chaos
  • Embedded UI thinking (real constraints)

Next steps

  • Quick rider usability sessions (5–8 riders)
  • Sunlight contrast checks + night dimming tests
  • Refine animations for peripheral vision
  • Validate layouts across riding modes
